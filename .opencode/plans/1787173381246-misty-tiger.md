# Plan: 7 agentes especializados de proyecto (creativos + estrictos)

## Objetivo

Reemplazar los 10 agentes-stub de `.opencode/agents/` por 7 agentes especializados del dominio de ProjectLove, con frontmatter válido (hoy no lo tienen → opencode los descarta en silencio) y prompts en español. Split de comportamiento: **3 creativos** (ui-ux, motion-design, responsive-design) y **4 estrictos** (frontend, accessibility, web-performance, geolocation).

## Mecanismo verificado

- opencode escanea `{agent,agents}/**/*.md` recursivamente (`packages/opencode/src/config/agent.ts:13`).
- Nombre del agente = ruta relativa sin `.md` (`configEntryNameFromPath`). Archivos planos en `.opencode/agents/` → nombre limpio (`frontend`, `ui-ux`, …).
- Sin frontmatter válido, `ConfigMarkdown.parse` falla y el archivo se salta (`agent.ts:19-20`). Los 10 actuales no están operativos.
- Formato de `permission` en markdown: `permission: { tool: { "patrón": "allow|ask|deny" } }` — string actions, **NO** arrays `{pattern, allow}`. Última regla que matchea gana → poner `"*"` primero y las específicas después.
- Temperatura: 0.1-0.2 = estricto/determinista; 0.6-0.8 = creativo.

## Estructura del prompt (cuerpo, en español)

Frontmatter común: `description` (una línea, gatillos al frente en español + sinónimos en inglés — la auto-invocación de subagentes matchea por este texto), `mode`, `temperature`, `permission`, `color`.

### Template CREATIVO (ui-ux, motion-design, responsive-design)
1. **Rol** — especialista de ProjectLove (OurStory), Fase 0: DEFINES diseño, no lo implementas. Entregables en `docs/`.
2. **Fuentes obligatorias** — leer AGENTS.md; verificar el estado real de cada doc (PRD y ARCHITECTURE tienen contenido; DESIGN-DIRECTION y COMPONENT-SPEC son esqueletos; MOTION-SYSTEM, DATA-MODEL, PROXIMITY-SYSTEM, DECISIONS están "Pendiente de definir"). Referencia visual en `references/lovable/` (solo lectura).
3. **Conducta creativa** — propone SIEMPRE 2-3 direcciones (concepto / encaje con PRD / impacto en el sistema / riesgos); iniciativa para señalar oportunidades; inspiración externa citada; coherencia con la identidad aprobada.
4. **Límites** — solo edita `docs/**`; nunca `src/`, `public/`, `references/`, configs; bash denegado.
5. **Contrato de salida** — resumen ejecutivo, direcciones propuestas, recomendación clara, cambios concretos en docs/, estado de los docs consultados.

### Template ESTRICTO implementador (frontend, geolocation)
1. **Rol** — ejecutas órdenes del agente primario con precisión, sin añadidos.
2. **Fuentes obligatorias** — AGENTS.md + docs aplicables; si la spec requerida está vacía/esqueleto → DETENTE y reportá, no inventes specs/APIs/contratos.
3. **Conducta estricta** — ejecuta exactamente lo ordenado; sin scope creep, refactors oportunistas ni renombres; antes de empezar reformula la orden y enumera archivos; después verifica punto por punto contra la orden y la spec; respeta stack y decisiones documentadas; aplica reglas de AGENTS.md.
4. **Límites** — `src/**` + `docs/**`; nunca `references/**`.
5. **Contrato de salida** — qué se pidió/quié se hizo, archivos tocados, checklist de verificación, cómo se validó (comandos + resultado), riesgos/supuestos/specs faltantes.

### Template ESTRICTO auditor (accessibility, web-performance)
Mismo esqueleto estricto + sección de **evidencia**: auditorías basadas en mediciones reales (lighthouse/axe/tsc/build), criterios objetivos (WCAG / Core Web Vitals) con umbrales explícitos, hallazgos priorizados por severidad, **sin** editar `src/` (los fixes los implementa `frontend`).
